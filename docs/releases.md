# Releases

Release Please manages a single version for this Tauri application, starting from the existing `0.1.0`. Its Node strategy updates `package.json` and generates `CHANGELOG.md`; targeted JSON/TOML updaters synchronize Tauri's version, Cargo's package version and only the application's entry in Cargo.lock. The pnpm lockfile contains no root package version and needs no version-only change.

The Cargo.lock JSONPath filter uses `name.value` because Release Please's TOML parser wraps scalar values with source-position metadata. Do not simplify it to `name`; run the updater validation when changing this configuration.

## Version policy

Use Conventional Commits as described in [AGENTS.md](../AGENTS.md). `fix` and `perf` increment patch; `feat` increments minor. Incompatible changes marked with `!` or a `BREAKING CHANGE:` footer increment minor before 1.0 and major from 1.0 onward. Internal maintenance types do not independently create a release. The highest applicable increment wins when several changes are released together.

The manifest records the current version, not a forced next version. With no existing release tags, the first PR can include earlier Conventional Commits from the repository history. Existing nonconventional commit messages are not retroactively rewritten. New changes must follow the convention, including squash commit titles and breaking-change footers. Release Please generates the first changelog automatically.

## Activate in GitHub

1. Commit/push this configuration to `main`, preserving any other work according to its own scope.
2. In **Settings → Actions → General → Workflow permissions**, enable **Allow GitHub Actions to create and approve pull requests**. Organization policy must also permit this. The workflow declares its required token permissions; no personal access token is required.
3. Make a release-worthy Conventional Commit. On pushes to `main`, Release Please opens or updates a release PR with synchronized versions and release notes. Review that PR and merge it when ready to publish.

There is no npm publication and no automatic merge of release PRs. The automatically created tag uses `vX.Y.Z` without a package prefix.

## Windows executable

After a release PR is merged, Release Please creates the GitHub release and outputs its tag. The same workflow explicitly calls `build.yml` with that tag. This avoids relying on a second event generated by `GITHUB_TOKEN`, which does not normally trigger another workflow.

The Windows job checks out that exact tag, verifies all four application version fields agree with it, installs frozen pnpm dependencies and runs the existing `pnpm run tauri build -- --no-bundle` command. It preserves the Actions artifact and attaches `proxytools-vX.Y.Z-windows-x64.exe` to the release's **Assets**. This remains a standalone EXE build, not an installer build or a signed executable.

The application discovers these assets through the GitHub API and verifies their GitHub-provided SHA-256 digest before offering manual executable replacement. Keep the release asset naming convention unchanged unless the application's downloader is updated with it. See [application updates](app-updates.md).

The release is published before compilation completes. If compilation/upload fails, the release remains available but may have no executable yet. Re-run the failed Windows job, or run **Build Windows EXE** manually with the existing tag in `release_tag`. Upload uses `--clobber` to support retrying the same asset. Leaving the manual tag empty builds the selected workflow ref and produces only an Actions artifact.

## Validation

Use actionlint on both workflows. Test the Release Please Node strategy and extra-file updaters without contacting the repository API: verify fix/perf patch bumps, feat minor bumps, maintenance-only suppression, breaking changes before/after 1.0, tag naming, and synchronization of all application versions without changing dependency versions. Actual release creation and Windows compilation require a workflow run in GitHub after this configuration is pushed.

`scripts/validate-release.cjs` performs these checks using the actual Release Please library. Install validation-only dependencies outside the application, then run from the repository root (Linux/macOS):

```sh
npm install --prefix /tmp/proxytools-release-validation --ignore-scripts --no-audit --no-fund release-please@17.3.0 ajv@8 yaml@2
NODE_PATH=/tmp/proxytools-release-validation/node_modules node scripts/validate-release.cjs
actionlint .github/workflows/release-please.yml .github/workflows/build.yml
```

On Windows, install those packages into a temporary directory and set `$env:NODE_PATH` to its `node_modules` directory before running the same Node script. These tools are not runtime dependencies and must not change the application's package files or lockfiles.
